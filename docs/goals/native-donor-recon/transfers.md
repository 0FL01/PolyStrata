# Two different costs: predicting demand and getting usable bytes to a consumer

**Do not port the donor's GPU cache as a replacement for host experts.** A correct prediction can still be late, or move 4.5 MB to a device that didn't need it. Conversely, a faster required copy needn't involve prediction at all. These separate experiments used the RX 6700 XT and the native host; none times an engine with speculative H2D enabled.

**Demand on a complete short trajectory.** Scratch capture of the older trace build on the same card and Tideglass v2.1, mixed 2K, 64 W1 steps, no draft. Capture actual normalized input, router scores, selected IDs and CPU/slot/pending masks for *every* visit, including all-GPU ones. Full FP32 scoring of the **same** row recovered the ordered authoritative top eight in 2,961/2,961 checks (63 tokens × 47 edges). Supplying the **previous** visit's input instead recovered 73.6% of IDs on the 45 donor-enabled edges, but the exact set on only 172/2,835 and exact order on 3/2,835. The two core restart edges, which #214 deliberately skips, gave 38.7% and 50.2% overlap. 65/65 generated IDs matched the archived same-prompt run; just 1,270/3,072 ordered routes and 315/3,072 residency masks matched that archive. Use labels and hidden from the *same* trajectory, or independently check the full join, never align by output text alone.

Donor's 14,352/16,833 (85.3%) was consumption of issued prefetches, not recall of all missing experts. At K=4 the local 146.8 MB/token would require another **5.9 GB/s at 40 tokens/s**, before normal uploads. Filtering *before* taking K=4 instead of abstaining (four cold picks on almost every visit) raised recall to 76.9% but spent **807.5 MB/token**, 560.4 MB wrong. On recurrent passes, actual IDs twelve visits earlier are a weaker but cheaper comparator with far more lead time. [Separate 64K host hint and in-engine test](router.md).

**DMA on this runtime.** PCIe 4 ×16, HIP 7.13, default SDMA. 1/4/14/48 random unique experts and slots; the same immutable source offsets, lengths and destination offsets, opposing execution order, consumer on a separate stream, byte and untouched-slot checks. Real model layers 0/20: joined Q4_0 gate/up 2,985,984 bytes plus 1,658,880/1,492,992 down bytes; repeat with donor-exact synthetic NVFP4 (six descriptors, two four-byte scalars) and MXFP8 (four descriptors). Here `hipMemcpyBatchAsync` is exported even below the donor 7.14 compile gate; the experiment compared it **directly against C++ `hipMemcpyAsync`**, not Python `Tensor.copy_`.

- At 48 experts batching identical descriptors **added 0.38–0.39 ms** on Tideglass, **0.50/0.77 ms** on NVFP4/MXFP8. Eight guarded legs, no new warnings or stop reasons. Keep the loop. Don't confuse donor's 1K prefill 448.6→512.4 tok/s against Python with an advantage over our native implementation.
- Actually reducing the descriptor count gave **8.62 → 8.28 → 7.94 ms**: two pinned pieces per expert → one *already packed* contiguous source per slot → ideal contiguous bulk copy. The last requires contiguous destinations too. Packing 14 real experts into a bounce buffer with four streaming-store workers took **3.04 ms** without contention or **4.19 ms** with competing CPU expert work, *before* DMA. Donor-ready duplicate bank would take about 14.6 GiB pinned for its checkpoint; not an economical second representation on this 32 GiB host. Keep registered GGUF spans where available.
- Independent streams can overlap a synthetic compute interval and one upload (**511–517 → 319–325 µs** joint wall). The archived actual follower path had >21 ms of slack before settlement in the sampled transfers. A 2K code-trace deadline replay charging measured 196 µs p90 per pinned fragment gives **100 / 86 / 68%** of miss-positive windows completing all cap 1/2/4 oracle jobs when issued early, no competing bus traffic. With a 421 µs submit-to-ready sensitivity, late cap-one completion across traces falls to **0–15%**. No generated ID or E2E claim follows from synthetic overlap.

**Reopen only for a measured stall at first consumer.** Timestamp ready source → actual submit → completion → consumer with generations and all non-speculative transfers active. Compare native loop on registered spans, truly contiguous physical coalescing where layout permits, and no-op. Count late and wrong bytes, CPU compute and H2D overlap *on the same timeline* and cost of evicting a useful slot. Hold target backend/route/sum order fixed or classify this as an approximate policy needing independent agent grading.

**Where to spend the next MoE experiment instead.** The [earlier real 197K tool return](../2026-11-25-adaptive-global-kv/hybrid-decode.md) measured the 43 wide rows separately: on the H2 suffix arm expert staging/MMQ occupied 236 ms device union (169 ms copies) and 198 ms of host expert work was outside all device activity; 315 of 340 ms of apparent explicit wait was *already overlapped*. This was not the deployed dense W1 profile. For a new opt-in, prefer queuing/reusing **known demand within the wide batch** from immutable registered spans, with generation-fenced staging and the original order of accumulation. First repeat that timeline on the actual dense control and actual tool reply; if no consumer wait is exposed, don't build it. Measure post-tool TTFT, continued greedy IDs and successful end-to-end time, not aggregate H2D bandwidth.
