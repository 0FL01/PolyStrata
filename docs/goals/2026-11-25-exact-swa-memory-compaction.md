# Exact SWA Memory Compaction — RECON 2026-11-25

Протокол и план для владельца движка, не изменение production. Исходный main `58046bbf`, RX 6700 XT 12 GiB (gfx1031), Ryzen 7 5700X, реальный Tideglass-Inkling-2-Mini-Unbound-v2.1, контекст до 200000, Q8_0 KV, prefill batch 2048, если не оговорено иначе. Имена прототипов и артефактов в обратных кавычках относятся к локальному исследованию `swa-recon-20261125`, не к файлам в этом репозитории. Здесь опубликованы результаты и условия их проверки, а не модель, сессии или сырые logits. Продолжение — [Adaptive Global Attention & Hierarchical KV](2026-11-25-adaptive-global-kv/README.md).

**Решение:** делать компактные независимые rings и общий contiguous stage, а при batch 2048 брать stage из уже использованного `input_[0]`. На реальном cold 64K это дало **−170 MiB resident** при идентичном размещении и побайтово одинаковом состоянии (с отдельным scratch — −164 MiB). Не переводить дополнительные CPU experts на GPU в режиме exact. По самой SWA нет основания обещать заметное ускорение длинного decode. Итоговые E2E-цифры и условия приведены ниже.

## Из чего исходили

`58046bbf` описал граф 48 visits в `docs/INKLING2.md`; `7a62d57d` зафиксировал Agent Mode; `50effa3a` изменил sampler, а не математику экспертов. В архитектурном RECON (`db7046a7`, `a36970f9`, `55a1eeba`) самые дорогие резервы decode были на стыке CPU experts/GPU и в full attention; на настоящем expert 116 даже при совпадении 2304 входных кодов gate отличался в 1152/1152 строках между backend. Скорость предыдущего RECON не используется вместо сегодняшнего A. Исходная 64K coding-траектория из Agent Mode упёрлась в лимит: её длительность не является временем решения задачи.

## Layout и инварианты для реализации

1. На `src/poly/inkling2.cu::alloc_caches` учесть **логические** visits: 40 локальных, восемь full, всего 24 набора весов. Между вызовами на позиции `p` следующий локальный query приносит свою строку, требуется `[max(0,p-1023),p)`. Внутри вызова длины `n` после групповой записи union длиннее: до `1023+n` строк. Делить scratch на `st_` в `run_visits()` безопасно, делить committed bytes разных visits — нет. K codes/scales/V codes/scales: 1024/64/1024/64 байт на строку. Новая квантовка недопустима.
2. Простейшая интеграция — `R=min(context,1023+t)`, `t=1` без draft, до 8 с DSpark. Сохранять прямой адрес `key % R` в serial и для verifier. Для больших вызовов — четыре смежные плоскости одного workspace. Gather старого хвоста, исходный `store`/`store2_q8` в новую область, исходная attention, один kernel для commit новых удерживаемых строк. Горячая heads/KV-запись остаётся прямой. Локальное начало scratch выбирать с фазой `first % 16`: сдвиг на произвольный `first` меняет дерево Flash. Сохранить абсолютные позиции для relative bias и исходное число decode chunks: target Inkling не использует RoPE. Никаких token-substitution, изменения prompt-batch, или смешивания результатов partial sums. При маленьких context/batch включать только если весь layout меньше исходного; когда union помещается, обходить stage.
3. `window(t)` до `keep(k)` уже записал все `t` строк. Один ring на 1024 без защиты уже повреждает старый хвост на частичном accept при ширине ≥2. В `R=1023+t` после `keep` отброшенный suffix вне диапазона, далее перезаписывается. Конволюционные snap/keep и собственный draft-KV (ему нужны 1024 старых) не менять. После сбоя восстанавливать последний committed checkpoint, не делать вид, что `keep(0)` транзакционен.
4. `ring_state/save_layer/load_extra`: тот же canonical oldest-first `min(context,1023)` tail на каждый visit/plane, нули слева в коротком префиксе. `try_pack_state` должен проверять фактические доступные плоскости/размер, а не конкретный старый modulus; сохранить staging, порядок queue и формат disk identity (включая prompt batch). `Engine::read` в looped режиме режет на границах marks и прогоняет visits chunk-major. Prefix reuse/парковка опираются на логические state/full rows, не на сохранение адресов scratch. Восемь full KV и conv отдельно; ни VMM-рост полного KV, ни размер disk image не должны «уменьшиться» от короткого SWA ring.

## Отбор реализаций на GPU

**Последняя итерация, `../swa-engine/experiment-v3/`, `q64borrow`:** нет необходимости добавлять allocation даже под общий stage. На SWA visit последний потребитель исходного `input_[0]` — sink projection; после него Q/K/V/relative/output/FFN пользуются другими slices, следующий writer на том же `st_`. У shared stage 6,715,136 B, у `input_[0]` при batch 2048 — 18,874,368 B. Borrow разрешён только когда вся область входит и выровнена; Q8 fit от 321 строки, FP16 от 831. Иначе выделить отдельный stage или оставить stock. В no-draft Q8 **все постоянные target SWA KV занимают 85 MiB**, дополнительный scratch allocation — **0 MiB**, но чтения и D2D gather/commit *остались*. На fresh mixed 65536, 65 output IDs, девять полных FP32 строк и все 40 SWA tails / весь saved state `12465d03…` равны A и B; также равны все per-eval layout fingerprints. Фактический process READY/end: на 170.00/169.98 MiB меньше stock. Cold TTFT 76.176 с, PP 860.40 ток/с против 76.503 с / 856.72 у stock и 76.405 с / 857.82 у dedicated: одиночный screen, не обещание speedup. `../swa-state/ds-v3-gate-1`: повтор строгого DSpark gate с реально включённым borrow дал 111/111 записей byte-identical исходной контрольной ленте; не только no-draft.

`guard-foot/command.log`: hipMalloc+touch+synchronize, изменение per-process `drm-resident-vram`, порядок выделений развёрнут. Stock 254.917 MiB payload / 256 MiB resident. 40×1024 = 85 MiB; общая входная extension = ещё ~4.25 MiB; отдельные allocation дали 92 MiB resident, slab — 90 MiB. Общий full-stage без phase padding ~91.37 MiB payload / 94 MiB при отдельных allocation. Реальный contiguous прототип резервирует ещё 15 строк под фазу: workspace 6,715,136 B, расчёт всего 91.41 MiB. При одном startup cap A/B (1143 одинаково ранжированных slots) READY процесса в первом engine screen уменьшился на **164 MiB**; повтор с +162 MiB дал 1181 (+38) startup slots. Это не количество дополнительных исполняемых experts на каждом длинном запросе.

`g-mic-check`, `g-mic-plain`, `g-mic-fp16`, `g-mic-vmm`: настоящие production attention kernels, синтетические полные плоскости; одинаковы FP32 outputs, fused Q8_1 где применимо, и committed bytes; основная сетка `n=1,7,31,32,257,1024,2048`, `p=0,17,65569,66559`. Клонированные split-address readers меняли только выбор строки. VMM double map подтвердил alias, но для scale stride=64 при granularity 4096 нужно кратно 64 строкам; отдельное отображение хвоста произвольной длины не бесплатное решение.

Dedicated spare экономит 146.01 MiB; заём действительно мёртвой второй половины residual — 148.67, но требует доказать lifetime. Для промежуточных ширин — точные subtiles/fallback. На двух реальных сохранённых KV CPU-сравнение 16.85 GB, 2960 хвостов. На gfx1031 все восемь H2 форм (`p=0…198011`) дали **0 отличий** у swap и subtile. Стоимость одного лишь warm H2 при p=65536,n=2048 3.2772 → 3.1030 мс/visit; p=65535,n=2047 3.2951 → 3.1893. Это не end-to-end и не время store. Испытывать более сложный вариант только против измеренного contiguous, не против старого best-case.

## Выделенная память ≠ точная смена placement

На 64K restored v2, даже при 65/65 одинаковых greedy IDs B и C отличаются существенно: позиция 65792 ещё побайтно одинакова, но **65793** даёт **200057/200058** отличающихся значений FP32, max `|Δ logit|=1.004919`; на 65794 `max=3.121041`. Исходный снимок и fed IDs одинаковы. Между A и B совпали 65 output IDs, девять захваченных FP32 строк и per-eval resident fingerprints. C нельзя называть exact, даже когда текст совпал.

Чем отличается физически финансируемый вариант D: из 24960 expert lookups при 65 последовательных eval (включая последний prompt ID) hits B→D составили 16713→16849 на 64K, 14475→14708 на 128K, 11161→11492 near-200K. Это дополнительно **2.09 / 3.58 / 5.09 hits на eval**; не 30–38 замен на каждый токен. После прогона оставалось ~36 MiB экономии относительно A, т.е. D действительно умещается. В отличие от оценки по GGUF, это измерение на настоящих маршрутах каждого из трёх контекстов.

GGUF: padded slot 4,479,264 B для 21 physical layers, 4,645,440 B для первых трёх. `fill_expert_cache` происходит после allocation SWA; выбор по use/byte. `cover()` на росте full KV уменьшает cache целыми ~64 MiB частями и перемещает горячие слоты; `mind_card_vram()` может докупить их обратно. Капнуть только startup arena **недостаточно**: v1 `parity-64-{A,B}` при 4900 MiB на обоих дал разные hits (18159/18377 из 24960), разные FP32 уже в первом слове при **одинаковых 65 ID**. На 2304→4358 при одинаковых per-eval resident fingerprints в prefill, но свободном CPU-share, расхождение ID на индексе 46; resave до новых вычислений совпал байт-в-байт с исходным `6fbe8913…`. Следует фиксировать и суммарный budget после `cover`, и GPU/CPU решения внутри prompt. Для естественной policy измерять отдельно; live share не подменять принудительным выводом модели.

`../swa-placement/results.txt`: на исторических 64K routed IDs добавление 39 слотов по другой train выборке убрало бы 3.45 (mixed) / 2.33 (code) CPU expert executions/token, gross прогноз всего 0.377 / 0.211 мс, не выигрыш wall-clock. Простой точный victim cache, меняющий только источник копии без изменения вычислителя, на 256+256 токенах дал 6/966 и 9/985 LRU hits (`victim.txt`), 0.10/0.15 MiB/token меньше H2D; не рекомендован как основная ставка. При жёстком требовании к исходным logits оставить extra bytes резервом или использовать для неизменной передачи/temporary workspaces. Перенос на GPU поверх исходного CPU-expert графа — отдельная research gate, нужно доказать каждый quant/dot/SiTU/down/sum для обоих типов, а не утверждать эквивалентность по среднему score.

## Проверки, которые действительно дошли до model state

* На near-cap `capend{A,B}`: из того же 199104-ID release snapshot прибавили 611 живых входов и 48 decode steps. Совпали карты, все 49 выданных IDs, девять logit rows и **все 3,571,169,428 B** сохранённой сессии на 199763 (`2063c291…`), включая 40/40 хвостов. Существенная оговорка по скорости: native request→первый ID **3.325 → 3.490 с** (−4.7% по скорости в этой паре), не считая RESTORE. Это mixed prefix extension с небольшим новым chunk, а не cold 200K. Не утверждаем отсутствие регрессии на всех prefill shapes.
* В `xrestore{0,1}` исходный сохранённый compact-файл загружен stock-бэкендом и наоборот; немедленный SAVE вернул SHA исходного файла `bf98397a…`. Затем одинаковое продолжение 65 prompt + 16 decode steps: одинаковы 17 возвращённых ID, все 9 FP32 строк, 40/40 хвостов и весь новый `40487ad1…` state. `borrow{0,1}` независимо изолирует один только borrow на одинаковой сборке: ещё **−6 MiB resident**, все 41 ID, FP32 выборка и весь `0939943e…` state совпали. Не сравнивать этот короткий v3-run с v1 без v2 бюджетного контроля: это другой placement.

* Два отдельных независимых prefill (4527 входных токенов в каждом) + 40 decode steps, batch 2048 и 257. Для этого контроля batched CPU-share установлен в 0, serial не изменён, profile seed одинаков; фактические per-call layout fingerprints совпадают. В обеих парах 41/41 greedy output IDs, 9×200058 полных FP32 logits, canonical conv, 40/40 SWA images, full KV и весь файл `STRSESS` совпали. Сравнивать `u2048-0` с `j2048-1` (SHA всего state `bf98397a…`) и `j257-0` с `j257-1` (`6f86778a…`). Разница READY/конечного per-process resident A→B −164/−164 MiB при 2048, −18/−18 MiB при 257. Не сравнивать ID между *разными* prompt-batch: меняются dispatch и session identity.
* `../swa-state/ds-fixed3-{0,1}`: реальный target и DSpark Q8/F16-head, 8192 context, batch 2048, одинаковые 280 slots, verify 8. Compact R=1031. Сверены **111 записей, 2,019,990,108 B**, включая 39 полных FP32 logit vectors и greedy IDs, 20 checkpoint images, пять proposal ID/probabilities и full KV. Обе границы ring, partial/full keep, перезапись rejected suffix, отмена, replay, sliced restore. Байтовых различий нет. Первый тестовый driver был слинкован с несовместимым определением Engine: число слотов 601882624 вместо 817 показало ошибку ABI в baseline. Приняты только данные согласованной пересборки. Эта проверка про state, не про скорость speculative decoding.
* В коротком sampled tool loop `../swa-agent/v1-short` дважды получен правильный Python clamp (проверка на 34 входах); по 31 reasoning ID, 6.466 и 6.500 с до успеха. Разные expert assignments — не утверждение о точной скорости. В другом, необрезанном по содержанию, но ограниченном по длине `read_case` (`readcase0`) reasoning исчерпал 1023 выходных токена второй реплики; у этого прогона **нет времени до успешного решения**.
* Все device прогоны обёрнуты `rdna2-rnd/scripts/run_guarded.py --warn-amdgpu-faults`. Естественную uncapped серию остановили на `g-uncap64-1` при падении общего free VRAM ниже 1536 MiB. Результат этого B не принимается; резерв и порог не снижались. Для реконструкции эффекта перераспределения — отдельный измеримый бюджет и проверка фактических slots, не экстраполяция этого uncapped результата.

## Что делать в движке и в каком порядке

**Критерий остановки:** близкий к нулю прогноз по measured W1 (~0.01 мс/token на runtime ring geometry, максимум около 0.04 мс/token для отдельной mask-специализации на 1024) значительно меньше observed run-to-run. Например, 64K A без изменения кода дал 32.13 и 28.01 ток/с; фиксированный B — 26.31 и 33.00. Порядок ABCCBA не превращает два повтора в доверительный интервал. Поэтому основание принять memory feature — измеренная экономия, байтовая эквивалентность и приемлемые SLO по новой серии, **не** усреднённое ускорение из этой шумной ячейки.

GPU jobs сериализованы, но это рабочая станция, не изолированный CPU: частоты, конкуренция host tasks и page cache не зафиксированы. В следующем release-speed gate не совмещать с линковкой/хешированием, фиксировать частоты/температуру и run-to-run A/A; включать 64K cold agent отдельно от decode из restore. Эти ограничения влияют на wall-time, а не на прямую сверку байтов артефактов или количеств resident slots.

1. Первый production-кандидат — opt-in только для target SWA. Выделить простой descriptor для четырёх плоскостей и для каждой операции явно различать абсолютную позицию и физическую строку. Не менять квантование, семантику checkpoint, расход полного KV, CPU/GPU math или текущий путь при выключенном флаге. Сохранять DD-очередность на `st_`, не добавлять `hipDeviceSynchronize` на visit. Гейт экономии — фактический размер рабочего набора **с** scratch, не только `R<old_ring`.
2. Задать независимую policy для памяти. В режиме headroom не давать `fill_expert_cache`, `cover` и `mind_card_vram` приписать себе эту разницу, включая рост после tool reply и возвращение stage. Хранить «как до compaction» бюджет для решений о размещении, но реальные проверки давления выполнять по действительной памяти. Сверять identities/backend/offsets, не только число слотов. **Replay измерительного стенда не является production feature**. Если исходное решение о CPU-share или переносе зависело от тайминга, два независимых stock запроса сами не гарантируют одинаковую траекторию. Обещание битовой эквивалентности формулировать при одинаковых решениях о вычислителе; не обещать детерминированную генерацию, просто сменив размер ring. Отдельный throughput-mode с реинвестированием — только осознанный opt-in, не «exact answers».
3. Gate для merge: те же prompts, профиль и seed, сверить default против выпущенной сборки отдельно от same-binary off/on; смотреть исходную FP32 строку и все четыре плоскости отдельно при первом расхождении. Проверить canonical SAVE в обе стороны, prefix mark, cancel/partial accept, ранний нулевой префикс, wrap, width 31/32, 1023/1024 и максимальный batch, fallback малых C/FP16. Для `--batch` с несколькими последовательностями/нескольких карт не обещать поддержку сверх существующих ограничений Inkling. Plain, decode, H2 и DSpark не смешивать в одном расчёте скорости.
4. Для speed gate брать A/A, затем A/B и B/A **без** logits/state dumps, одинаковые free reserve, размещение при restore/verify и одинаковые backend decisions на prompt. Отдельно рунами B/C оценивать extra cache: p50/p90, TG, slot count и hits, первый разошедшийся logit/ID, обе полные tool траектории, время и reasoning до прохождения независимой проверки. Не усреднять быстрый/неудачный/обрезанный ответ с успешным, и не трактовать меньше reasoning как улучшение модели. Оставить единственным заявленным результатом экономию VRAM, если улучшение wall/агентского p90 не повторится относительно A/A. Для ускорения сверх этой границы следующие объекты профилирования — full attention и exposed CPU late, не SWA адресная арифметика.

## Артефакты и интерпретация прогонов

### Контроль реально оплаченной ёмкости

C прибавил 162 MiB к *расчётному* budget, но из-за округления `cover()` удержал на 192 MiB больше expert mappings, чем B: на длинном restore процесс C оказался примерно на **28 MiB больше A**, хотя на READY они почти равны. Поэтому запущен четвёртый вариант D, cap 5028 MiB: +128 к B, без превышения исходного footprint. Это отдельные untraced запуски по 256 интервалов в прямом и обратном порядке позиций.
