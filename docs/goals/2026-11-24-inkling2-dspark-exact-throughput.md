# Goal: faster exact Inkling DSpark decode on RDNA2

Status: active (exact drafter wins deployed; adaptive rollout gate not met)
Source: user request to raise DSpark decode t/s without divergence, then iterate from RECON through measured prototypes; commit, push, deploy, and reprofile each confirmed win. The RECON plan is a map of hypotheses, not a fixed implementation order.
Last updated: 2026-11-24

## Objective

Raise end-to-end decode throughput for Inkling-2-Mini Q4_0 with native DSpark on the RX 6700 XT without changing the target answer. Keep the default serial deployment until speculation matches it with live swaps and clears the prior rollout gate.

## Required outcomes

- R1: Keep only reproducible decode wins with exact relevant boundaries and greedy token IDs on gfx1031. Evidence: untraced paired engine runs, token IDs, and the closest kernel/state check; report losses and limitations. Status: verified for the two drafter attention changes under the fixed-schedule control.
- R2: Push each qualified change to `origin/main`, build Release, deploy that binary without unqualified configuration changes, and use it as the next baseline. `6f233b3e` and `0b49a9c6` pushed and deployed; latest gfx1031 Release SHA-256 `97441b0912a0ad913a224499bbf90c6053b953ba92f68350b2bb5fa70bffd5b6`. `/health` loaded the 200K configuration and chat emitted 64 tokens after each deploy. Status: verified for both attention changes.
- R3: Qualify live speculative verification against serial, then measure adaptive decode against plain. Evidence: greedy IDs, fixed-seed sampler, committed state, and tool/code/JSON and 16K speed gate from the prior [DSpark goal](2026-11-24-inkling2-dspark-disk.md). Status: blocked for rollout. The tested exact verifier is slower than serial; the stock adaptive verifier is not serial-exact on the checked trajectories.

## Scope and checkpoint

`src/poly/inkling_dspark.cu`, the native Inkling verifier and its expert kernels, and affected documentation; use isolated prototypes outside the source tree. Keep model, precision, reduction order, routing/sampling, disk format, VRAM reserve and default no-drafter path unchanged unless separately proven exact. Serial GPU runs with the existing guard; no gfx1031 performance counters (`rocprofv3 --pmc`).

Complete the smallest unresolved outcome; let measured results choose the next experiment rather than following a fixed route. Stop a line of work that cannot meet exactness or end-to-end speed in its envelope; don't treat a leaf win as a rollout result.

Current checkpoint (R1/R2/R3): ship the opt-in long target attention dispatch after checking the Release build. Retest the serial placement oracle with a capped, matched A/A before interpreting its cost. RECON traces, guarded scripts and the row-geometry parity cases are indexed in `~/.cache/opencode-tmp/opencode/dspark-profile-next/PLAN.md`; the new scratch sources are in `dspark-impl-gpu`, `dspark-impl-oracle` and `dspark-impl-host` under the same parent directory.

In the probe, the first drafter attention variant preserved all FP32 intermediate/output bytes and reduced the 64K engine dispatch from 11.84 to 7.27 ms. The separate Q4_0 verifier tile leaf was exact; front-wait removal and commit fusion did not improve decode.
- Checkpoint 1 (R1): integrated gfx1031 value reuse behind `STRATA_INKLING_DSPARK_REUSE_V=1`. Other live runs varied even in A/A; do not infer adaptive parity from these numbers. An isolated frozen 64K confirmation was stopped at 1,433 MiB free by the guard, with no GPU fault; use reduced arena and no direct staging in the next 64K control.
- Checkpoint 2 (R1/R3): with the value-reuse build, fixed 64K ROCm trace measured 12.271 → 7.432 ms for full drafter attention and 17.049 → 12.266 ms for the warm first proposal; traced width-4 target verification is still about 106 ms (frozen placement; not production latency). At 2K/16K, 42/58 of 106 windows replayed the second row for a placement mismatch. Production verifier is unchanged.

## Closeout

Keep both opt-in attention changes. The direct before/after Release-derived control gives +7.22% decode at 64K with equal outputs and checked state. Do not activate native DSpark in the default deployment. The remaining cost is in the target verification path, not a shortage of correct guesses alone: on the checked 2K adaptive exact run, 44 of 46 guesses were correct, but 15 windows needed a serial replay. Neither the measured replay costs nor the best remaining leaf savings support the rollout target in the tested design. Reopen for a verifier that avoids paying for the same target row twice while preserving the serial expert decisions and accumulation order; first require live bitwise parity and a measured wall-time break-even. This is not a claim that other verifier designs cannot meet the gate.
