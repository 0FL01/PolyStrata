# Какие биты и страницы стоит читать

Дополнение к [плану для RX 6700 XT](hybrid-decode.md). Не путать три измерения: отклонение результата **одного** attention на фиксированных Q, latency его device kernel, и сохранение качества всей свободной trajectory.

## Точность и бюджет

Реальные Q, K/V, relative, sink и gate: 10 predictor positions, восемь global visits, все 24 Q heads. В том числе вызов инструмента, ответ после инструмента и два near-197K post-tool predictors. Все 80 текущих строк совпали со snapshot, CPU dense с GPU output — до `6.42e-6` relative L2. Проверены pack/unpack на 32768 реальных строках KV heads. Это всего три trajectories; у Code и long-code общие 65606 начальных ID, у Reason и Code — 617. Проектируемая экономия ниже относится к **190848 холодным строкам** из 199104, остальные 8256 остаются Q8; учитывает коды и метаданные, но не VMM, индексы и размещение экспертов. Исторические **769.5** MiB физического symmetric V4 относятся к другой границе (196992) и не являются числом этой таблицы.

| Холодные K / V | Прогноз экономии MiB | Near-197K gated relative L2, p95 / max |
|---|---:|---:|
| Q8 / affine4, 16 features | 466 | 3.80 / 6.32% |
| Q8 / affine4, 32 | 652 | 4.62 / 12.2% |
| Q8 / symmetric refit4, 32 | 746 | 6.85 / 16.6% |
| K6 channel-affine / affine4, 32 | 932 | 4.76 / 12.4% |
| K4 channel-affine / affine4, 32 | 1305 | 6.96 / 22.0% |
| Q8 / affine2 + один outlier на 32 | 885 | 19.5 / 39.3% |

При неизменном K не меняется score на том же входе; V4 всё равно меняет следующий hidden state. K6 меняет и распределение softmax. В канальном формате K min/scale приходятся на блок из **32 последовательных токенов**, V — на соседние признаки одного токена. Включать полный Q8 K сначала: так index строится по настоящим K, а не по приближению к приближению. Для K6 явно выбрать источник centroids, включить его стоимость в бюджет и проверять rank ID и ошибки вместе.

Различие visits реально, но это не готовая политика. У K4/V4 на near-197K p95 по visits 5…47 — **9.93 / 5.82 / 6.07 / 5.09 / 4.88 / 4.11 / 5.85 / 13.0%**. При равном среднем 192 B на cold token × KV head настройка по Code снижает свой p95 с 3.57 до 3.17% (visits) / 2.74% (groups), но независимые по фазе near-cap значения **4.76 → 5.16 / 5.08%**. Для 8 особо чувствительных каналов медианное пересечение train/перенастройка на held-out — 4 из 8. Маска немного снижает near-197K K4 p95 (6.96 → 6.61%), но ухудшает худший Reason head. Отдельный V4 residual дороже и хуже plain affine4-32. У K4 base + 2 refinement bits чтение обеих плоскостей на каждой второй странице даёт p95 5.90% на long-code, но если все младшие биты остаются в VRAM, **ёмкость всё ещё K6**, а если выброшены, query не может их вернуть. Сейчас не стоит платить scatter, метаданные и разноразмерные ветки для десятков отдельных групп.

**Что взяли из работ.** [MixKVQ](https://aclanthology.org/2026.acl-long.326/) связывает `mean(|Q_d|)` с диапазоном канала K, а [KVQuant](https://arxiv.org/abs/2401.18079) калибрует некруглые уровни и выбросы; для target Inkling нет вращения RoPE, а projected sink не имеет строки V. [KIVI](https://proceedings.mlr.press/v235/liu24bz.html) мотивирует разные оси группировки K и V. По [KVTuner](https://proceedings.mlr.press/v267/li25dd.html) поиск по слоям требует **после** ошибки оператора проверить генерацию; физический слой Inkling нельзя отождествлять с логическим visit. [PM-KVQ](https://proceedings.iclr.cc/paper_files/paper/2026/hash/afb8caec018d3c8f6ef8b81fa52386fe-Abstract-Conference.html) — прогрессирующее необратимое понижение при росте, а [ReadKV](https://arxiv.org/abs/2610.11245) — разная глубина **чтения сохранённых** битов K и V. Это разные эксперименты. Ни одна опубликованная скорость на другом GPU в наши прогнозы не переносилась.

## Проверка лучшего V4 по локальной точности в настоящем движке

Сделали affine V4-32 restore и оба reader, оставили тот же Q8 K и K256. FP16 minimum каждой группы **оплачен внутри VMM**, а не вынесен в бесплатный массив. Контроль с symmetric в одном ELF: идентичны списки страниц в паре на visit 5, pos 199105. По 24 Q heads ошибка против выбранного native Q8 на этом Q улучшилась с **12.06 до 8.45% p95**, max 16.33 → 11.48%. Проверены все байты кодов и обоих FP16 fields на 262144 реальных блоках; CPU с соответствующей деквантизацией воспроизводит GPU до `3.10e-6` abs. Это лучшее локальное представление, но **не лучший режим для этого железа**:

| Прямое сравнение symmetric → affine32 | Результат |
|---|---|
| 199104, физический KV, arena | **2550.81 → 2647.00 MiB**, из них +96.19 minima; слоты 536 → 521. С индексом, scratch и arena физически **4903.82 → 4936.01 MiB**. Экономия против native KV 769.50 → 673.31 MiB. |
| 199104 greedy, полная сборка | **25.93 → 24.52 ID/s**, полный RESTORE **3.95 → 6.91 s**; все 65/65 ID совпали. |
| 197021 original, seed 79 | Обе 1/1 pass, time-to-success **9.36 → 9.60 s**, с запуском 14.83 → 17.91. T1 48/48 одинаковы; T2 первое отличие на индексе 17. |
| 197021 board, seed 42 | Обе 1/1 pass, **8.74 → 8.46 s**, но с запуском 14.17 → 16.62. T1 38/38 одинаковы; T2 отличие на индексе 20, на 15 ID меньше. |

**Оставить symmetric.** Выигрыш в ошибке не вернул ни одного утраченного grade. Повторить affine имеет смысл именно на воспроизводимом отказе symmetric, если восстановление качества оправдает меньше слотов, более долгий RESTORE и PP. Не продолжать подбирать seed или ступени битности только ради улучшения одного L2.

## Сколько эти форматы стоят на RDNA2

Отдельный эксперимент с **реальным** full selected attention visit 5, не single-dot. Одинаковые device-picked K256/P128 для 16 Q на позициях 199104…199119, 35009–35024 строк на GQA group. У всех cold/hot split при 196992, обычные Q8 в хвосте. Здесь низкие биты — **row-refit** с FP16 scales, в частности K6 **не** channel-affine, а V2 **не** outlier-вариант из первой таблицы. В latency входят relative/softmax, sink, gate, combine и запись Q8_1; rank, pack, eviction и копирование — вне. По 96 HIP-event samples на arm/cache condition, два закрытых guarded запуска; replay сразу после того же запроса — лучший случай, не типичный токен.

| Формат | После eviction / немедленный replay p50, µs | Логический payload на visit, MiB | VGPR/SGPR |
|---|---:|---:|---:|
| Native Q8/Q8 | 307.84 / **225.84** | 72.666 | 175/46 |
| K8/V4 split | 304.92 / 243.50 | 56.604 | 170/26 |
| K8/V2 split | **291.22** / 238.42 | 48.572 | 168/26 |
| K6/V4 split | 319.50 / 261.46 | 48.572 | 168/26 |
| K4/V4 split | 294.12 / 242.98 | 40.541 | 166/26 |
| K8/V4 прежний reader, один launch | 329.18 / 275.16 | 56.604 | 183/50 |

Одна wave32 ведёт KV-группу, 8 lanes на один ключ, 16 dimensions на lane, один payload на три Q. K6 ложится в 12 B (`dwordx3`), nibble — 8 B, V2 — 4 B. При **тех же bytes** K6/V4 оказался медленнее K8/V2: 171 против 73 статических bit-style инструкций, включая адресацию; без spills у всех. Это согласуется с ценой unpack, но не является аппаратным счётчиком DRAM или динамических инструкций. Общие 3.42 MB chunk partials пишутся *помимо* KV. Важная проверка читателя: против FP64 CPU с соответствующим dequant максимальная абсолютная ошибка `3.18e-6`; это **не** сравнение качества V2 с Q8. У двух реализаций K8/V4 совпали все 49152 gated FP32 elements. Даже полные 24 µs на каждом из восьми visits — всего около 0.19 ms/token ожидаемой экономии от split, а не 7–12% ускорения движка. Поддерживать K6 ради вычислений не стоит; отдельный вопрос — окупятся ли дополнительные expert slots при достаточном качестве.

При долгом append старые, но ещё **V8**, страницы сами становятся кандидатами top-K. Граница cold/hot тогда на разных индексах списка у разных групп. Перенесли разбиение в движок без ошибки: из упорядоченных IDs известны гарантированные общий cold prefix и hot suffix; только между ними запускается прежний reader с проверкой формата на каждой wave. На 199104 + 128 W1 шагах понадобилось 528 таких неоднозначных chunks/leg (0.19%), без fallback целого шага. Все **129 ID** и количества выбранных строк совпали в четырёх ногах ABBA. Разница split−mixed −0.150 / −1.547 ms/token, но сам mixed-контроль между повторами изменился на **1.441 ms/token**. Интеграция корректно пересекла границу в этом тесте; небольшой E2E выигрыш **не установлен**, воспроизводить только вместе с более значимым изменением, не обещать ускорение по листовому kernel.

## Query-aware: что показывает настоящий Q

Другая серия: 36 позиций, шесть traces (agent code/reason/tool, mixed 64/128/199K), 6912 наблюдений head×visit×position; dense replay против записанного device output до `8.91e-6` relative L2. Page 0 и округлённый хвост ≥2048 закреплены; одинаковые абсолютные расстояния и projected sink. В таблицах replay считаются логические bytes выбранного Q8 KV, не транзакции GPU и не освобождённая VRAM.

- **K на visit / pass.** Перебрали все `5^8 = 390625` вариантов `K∈{32,64,128,192,256}`. Ни один более дешёвый вариант не оставил на **всех** шести traces relative p95 и p99 в пределах +1 п.п., absolute p95 в пределах +10% от свежего K256. На двух near-cap можно убрать 64 страницы только у visit 41: −17 MiB логических reads, около **0.058 ms/token** по ранее измеренному наклону leaf. Это основание не писать новый dispatch для этого grid, не доказательство оптимальности K256 вообще.
- **K на текущий query/group.** Истинная масса даёт 20.8 → 17.8% p95 на 197K при одинаковом объёме, но её вычисление уже требует старых scores. Доступная модель массы через две половины страницы: 29.0 → 27.6% p95 при **ухудшении** p99 50.2 → 53.5%, с **1.93×** padded rows в нынешнем прямоугольном grid. Покрытие по оценке 90% даёт на 64K code 11.6 → 28.5% p95. Нельзя давать гарантию ошибки от predicted mass. Независимый K256 на каждый Q head улучшил 197K p95 лишь до 27.7%, увеличив GQA union 582 → 872 MiB.
- **Иерархия и предыдущий Q.** При 8 дочерних страницах и 80 родителях на shortlist: 47.6 → 26.0 MiB metadata reads/token, 29.0 → 29.5% p95, второе ordering съедает часть выигрыша; оценка лишь **0.10 ms/token**. Один FP16 центроид всей страницы вместо двух центроидов её половин даёт 82.4% p95. Полный rank раз в 4 Q + свежие coarse candidates в промежутке: около 0.17 ms/token расчётной экономии, но отдельные неполные обновления теряют до 34 п.п. на code. Готовить кандидаты можно, использовать старый ответ без проверки нового Q — нет.
- **Уточнение K отдельно от V и вклад старой истории.** Храним `mean(V)` каждой страницы; для пропущенных страниц оцениваем `Ẑ` по текущему Q. Прибавляем `Ẑ` к знаменателю и `Ẑ·mean(V)` к числителю *до* нормализации, с точным sink и sigmoid gate. При K256 197K p95 29.0 → 25.4%, но +24.4 MiB index и работа по старым страницам, KV не освобождается. При K192 чтения 582 → 446 MiB, 197K p95 29.7%; на mixed199K p99 **42.2 → 52.4%**. Даже настоящая масса не восстанавливает условное среднее V. Перенос старого weighted result с dense refresh раз в 4 даёт 45.4% near-cap p95 и больше байтов, чем свежий K256. Смысл K-first/V-refinement — проверять качество *и* реальную цену второй стадии, masks, scratch и merge; не выдавать его за одноступенчатый формат.

**Вывод для плана:** оставить свежий K256/P128 опорой для оптимизации движка. Бюджетный поиск переоткрывать при достаточном выигрыше на критическом пути, на независимых распределениях Q, с ragged/bucketed GPU execution и новой проверкой свободных trajectory. Проверять самое слабое место (ошибка на редком tool/answer), а не только среднюю массу.
