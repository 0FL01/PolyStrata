# Adaptive Global Attention & Hierarchical KV — измеренный RECON

Продолжение: [Adaptive KV Precision & Hybrid Decode](hybrid-decode.md) сравнивает все четыре режима при одном лимите, отдельно измеряет ожидание CPU-экспертов после K256, восстановление V4, TTFT после tool return и свободные агентские траектории. Цифры ниже относятся к первоначальной серии и её контролям.

**Статус на 25 ноября 2026: измерения завершены, внедрение на паузе.** Главная метрика — время до правильного решения агентом на RX 6700 XT. Экспериментальные ядра, форматы и флаги не вошли в движок. Совпадение greedy ID само по себе не доказывает ни численной эквивалентности, ни сохранения качества.

Для передачи аналитику: [парные замеры и отказы](scoreboard.md) → [задачи с инструментами на длинной истории](long-context-tasks.md) → [приоритет следующей итерации](#приоритет-следующей-итерации). Предыстория: [архитектурный RECON](../2026-11-24-inkling2-architecture-aware-results.md), [Tideglass Agent Mode](../2026-11-25-tideglass-agent-mode.md), [Exact SWA Memory Compaction](../2026-11-25-exact-swa-memory-compaction.md). Имена сырых артефактов и прототипов в обратных кавычках — идентификаторы локального исследования `global-kv-20261125`, а не поставляемые команды. Для чтения отчёта локальный кеш не нужен.

**Первым проверять K256/P128 по двум центроидам страницы, оставив весь Q8 KV на карте.** На 197K он ускорил не только выдачу токенов: выигрыш в двух успешно решённых задачах составил 11.7–12.2%. В контрольной траектории совпали все 143 ID, в архивной он выиграл, даже потратив на 8 reasoning ID больше. Вторая, независимая опция — физически упаковывать старые V, не удаляя K и не теряя доступа ни к одной строке. Их **реально запущенная комбинация** на near-199K дала **26.01 против 20.75 ID/с** у того же V4 без отбора; на 197K исторический board прошла за **9.91 против 11.22 с**. Сравнения с Q8-K256 на строго общем cap/ELF для выбора между этими двумя политиками нет. Самая быстрая конфигурация на повторяющемся тексте — жёсткое окно с перераспределением памяти — **не** рабочая точка для общего агента. Ни стабилизации всего диапазона 64K–200K, ни большого выигрыша при строгой битовой точности пока не достигли. См. [итоговые пары и разделение затрат](#результаты-на-197k-и-пределы-выигрыша).

## Что действительно измеряет тест

* Восемь global visits `5,11,17,23,29,35,41,47`, два триплета shared weights, **ни одного shared KV state**. Три Q-heads на одну KV группу. Один и тот же query читает собственные абсолютные ключи, `dot/√128 + rel·table[delta]` только на δ<1024, один projected sink в знаменателе, нулевой value sink и покомпонентный sigmoid gate. Приближённому пути нельзя перенумеровкой старых страниц создавать новый relative bias. Перенос выбора между core passes — эвристика, не инвариант.
* `captures/{mixed64,mixed128,mixed200}/set`: для 16 последовательных настоящих шагов на позициях 65792/131328/199104 захвачены Q, relative query, sink, gate, добавленные четыре плоскости Q8_0 и настоящий FP32 output каждого из 8 visits. Старые K/V из канонических snapshots (пути в `seedpath.txt`, те же следующие входные ID). Получены также полные logits и 48×8 ordered route IDs/weights. Пары девяти полных dense logit rows во всех контекстах побайтно совпали с сохранённым dense control предыдущей кампании. При агрегации сужать сравнение logits до общего causal prefix включительно до первого разошедшегося выдаваемого ID: ниже него это уже другие входы.
* **Скрытая слабость прежнего long-context mixed корпуса:** из выровненных 128-token страниц **87.55%, 93.76%, 95.88%** на 64/128/near-200K уже встречались дословно в более ранней истории (любое выравнивание). У настоящей CPython tool-history 65,796 — **0/514**. В mixed вообще нет native message/turn delimiters. `diversity.py`, `diversity.txt`. Отличный тест линейного чтения KV, очень плохой тест retrieval/успеха агента. Например, первый near-cap dense logit top1=26.43, следующий 8.45. Ограничение всех восьми visits хвостом 8192 поменяло **176 из 384** выбранных экспертных ID (set difference внутри каждого visit) и до **6.504** в logits; top1 не поменялся. TV всего 2.84e−8 на этом предсказуемом токене. Отдельно проверяем agent history, разные этапы и независимую оценку задачи.
* Сильная повторяемость текста **не разрешает exact дедупликацию KV**. Для 512 равномерно взятых пар с тождественными предшествующими 128 ID, near-200K: **0/4096** полностью совпавших KV-head rows на каждом из восьми visits (коды и масштабы). Медианы relative L2 подстановки K/V от 1.6/1.9% на visit 5 до 53.4/74.0% на 35. `repeatkv.py`, `repeatkv.txt`. Это тест готового KV на последней строке одинаковой последовательности, не upper bound всех кодеков. Уникальные исходники агента вообще не дали таких 128-токенных пар.

## Системная цена выгрузки в RAM

На 199999 строках восемь global Q8_0 caches — 3320.30 MiB. Оставить только хвост 1024, а всё остальное каждый токен читать из RAM — **122–128 мс/ток только на доставку**, даже при bulk 27.0–28.3 GB/s. `dma/REPORT.md`, `methods.md`: три серии на gfx1031 с **272 MiB настоящих кодов и scales**. 4.25/17/68 MiB contiguous pinned H2D стоили 0.229–0.262 / 0.699–0.775 / 2.583–3.139 мс; CPU gather отдельных страниц перед отправкой — 0.267–0.570 / 1.331–2.484 / 8.133–10.382 мс. Интегральный восьмипоточный DDR4 read — 40.1–42.3 GB/s. Coalesced GPU read из mapped registered host memory на 17/68 MiB — 0.677–0.719/2.674–2.879 мс (read/XOR leaf, не интегрированная attention; без параллельных CPU экспертных dot). `hipMemcpyBatchAsync` не объединил трафик бесплатно. **Читаемые, пересылаемые и физически освобождённые байты — три разные метрики.** Считать реальный union страниц тройки Q-heads, и какие head slices переносит физический layout. Первичное архивирование 17 KiB/добавленную строку измерять отдельно от чтения старых страниц.

Проверка на настоящих page IDs, включая три Q на одну KV группу (`dma/CHURN.md`). Code, P32/B8192: shared oracle с cache размера последнего набора потребовал 118.5 MiB первичной загрузки, затем median/max **51.9/55.7 MiB**; Quest — 37.8/39.7 MiB, но хуже внимание. Если обслуживать page сразу для всех KV-heads, фактический union oracle дал 313.8 MiB сначала и 98.2/129.8 MiB в steady state. Настоящий LRU на 349 MiB снизил медиану misses до 28.6 MiB, не убрал хвост. Предзагрузка 32K-кандидатов для бюджета 8K: всего 6.5 MiB на demand, но **121.7 MiB на весь refresh**. На mixed200 с бюджетом 80K/P32: shared oracle потребовал 397.8/449.4 MiB median/max misses, **15–17 мс/ток** даже по пиковому bulk; это уже больше resident full-attention времени. Это воспроизведение реальных ID и перенос отдельно измеренной цены, не живая GPU attention с PCIe. В этой конфигурации cold offload не следующий шаг. Ни D2H-архив, ни спрятанный за MoE refresh не бесплатны.

## От массовой статистики к причинному тесту

`agent/CAPTURES.md`, `oracle/SUMMARY.md`: два естественных двухходовых 64K прогона с полноценной генерацией, живым инструментом, EOS и независимой проверкой ответа. Записаны все Q/K/V probes: 205/345 позиций × 8 visits. В каждой истории сверены более 1.14 GB переиспользованного через tool return KV. CPU oracle отдельно пересчитал все 24 output heads на четырёх последовательных позициях каждой из четырёх фаз в обоих запросах, плюс все mixed позиции — **15,360 head samples**, худшая относительная ошибка dense CPU против настоящего device output 6.17e−6. Речь о численной реконструкции, не побитовой.

| Бюджет 8192, P128 | Code: context mass p50 / gated rel. L2 p95 | Reason: то же |
|---|---:|---:|
| Истинный top страниц отдельно по Q-head | 95.9% / 28.7% | 92.8% / 31.5% |
| Истинный top по сумме трёх вероятностных масс в KV-group | 95.5% / 32.6% | 92.1% / 34.6% |
| Практический min/max Quest, общий бюджет группы | 88.3% / 54.2% | 77.9% / 59.5% |

У независимых heads «8K» по факту читает медианные 12.7K объединённых рядов одной группы. Даже P32/B32768 при идеальном per-head ранжировании даёт p95 5.5%/6.0% ошибки; oracle оптимален **по сохранённой массе**, не по ошибке value-вектора, logits или ответу. Головы с большим sink могут иметь большой relative error на маленьком абсолютном сигнале. Старый контекст нужен прежде всего **при генерации аргументов инструмента**: медианная масса за пределами последних 1024 — 80.4%/76.1% на code/reason, против 16.5%/22.5% в рассуждении после ответа. Это не универсальная граница между фазами: в каждом распределении есть тяжёлые хвосты. При закреплении только `turn_at` по последнему message-tool вся эта короткая фаза и так входила в последние 1024; это не эксперимент с длинным 64K user-turn. В stratified arms закрепляется вся последняя **user**-ветка, включая tool results.

Один и тот же физический вес имеет неодинаковую роль на разных проходах. Например, у visit 11→23→35 доля старой массы p50 на code 15.2→8.8→12.1%, p95 **97.6→88.2→87.5%**. Среди всех visits, 5 имеет p50 79.4%, а 47 у некоторых samples кладёт до p95 88.7% на sink. Общий Quest, предыдущий токен: median Jaccard 57.1/59.4%, p95 **приращения ошибки** относительно fresh selection +8.5/+15.2 п.п. Передавать ранжирование между core passes без проверки тоже нельзя. Даже если ranking нужен только для prefetch, нужно нагрузить бюджет полным refresh, не только demand misses.

**Адаптивное распределение одного общего бюджета.** `budget.py`: дискретный оптимизатор распределяет по 8 visits или 64 KV-groups от 2K до 32K, минимизируя средний квадрат относительной ошибки на *одной* истории. На независимом workload применены те же budgets и тот же total. Code→reason, group-Quest при среднем 8K: p95 59.53→55.15%, но медиана 14.98→17.12%; при среднем 16K p95 41.06→36.08%, медиана 8.60→9.74%. При среднем 8K уровни на один visit после обучения `[16,4,4,4,8,8,4,16] Ki`. Напротив, при переносе с repeated mixed на code p95 **54.19→55.36%**, при 16K **35.75→41.91%**. Поэтому раздавать классы навечно по mixed или объявлять head «локальным» по медиане нельзя. Это перераспределение количества рядов при query-aware отборе, не recency-only. Отдельные причинные interventions по 192 Q-heads и по одному из восьми visits проверяют logits/маршруты, а не только локальное L2 (`heads/*/impact.csv`, `digest.py`).

**Можно ли расширять бюджет до доказанной мягкой гарантии?** `certificate.py` / `certificate.txt`: на всех 8×24 heads проверили bound `upper = n_page exp(sum_d max(q_d min_d, q_d max_d)/sqrt(128))` для ещё не прочтённых старых страниц; в уже прочитанном знаменателе есть обязательный recent и настоящий sink. Критерий: верхняя оценка пропущенной массы ≤5%, не гарантия совпадения logits. На коде, reasoning и mixed200 даже при P16 **медиана требуемых страниц 100%** (5-й процентиль ≥99.5%); при P128 уже 5-й процентиль 100%. При известной *истинной* массе P16 медианы 5.1/3.4/6.7%, но p95 55.9/54.7/61.6%. Это практический провал именно extrema-сертификата, не доказательство невозможности любого индекса. Точный путь не превращается в sparse добавлением fallback: нужно померить, как часто и как поздно тот срабатывает.

## Что оставлять в холодной истории

`hierarchy/README.md`, `hierarchy/code-reason-phases.md` сравнивают K и V раздельно, эффект на softmax и на gated output, packed bytes и реальный CPU scan. На near200, 8K hot-Q8: channelwise K4/V8 — 80.3% native bytes, p95/max ошибки 6.44/15.0%; K8/affine V4 (16 признаков на scale/min) — 85.9%, 4.48/7.98%; K4/V4(32) — 60.5%, 8.28/15.8%; V2 + outlier — 73.2%, 25/33.5%. На настоящих code/reason четырёх фазах у K8/affine V4(16) worst 7.75%; на tool JSON p95 3.64/5.09%. У более дешёвого физического K8/V4-symmetric-refit при том же 8K hot worst 13.9%, на tool JSON p95 6.34/8.02%. Это разные codecs, и ни один не битово эквивалентен. K8 имеет особое достоинство: внутри *того же visit на том же Q* сохраняет все внимание/вероятности, но после изменённого V уже следующий Q/маршрут может быть другим. В packed CPU leaf (5700X, 199K, 3 heads/1 group) Q8 8.77 мс против 10.12–10.14 мс для one-sided Q4; меньше байтов не равняется меньшему времени.

Mean K/V на 64-токенных страницах с правильным ln(count) и Q8-hot: near200 размер 6.94%, но p95 87.1% и worst 120%. Даже **истинная** масса каждой страницы с её равномерным средним V даёт p95 99.1%. Уточнение top 20% по предсказанной массе: p95 22.2% и worst 64.1%, нужно хранить исходники + сводки (103% Q8); 26.1% чтения — оценка на один head, до GQA union и доставки. Однородные страницы по строгому фильтру сохранили лишь 0.0144% байтов; фильтр на 3.21% экономии уже дал p95 14.2%. Ни раздельные mean, ни малый diagonal variance не заменяют истинную условную weighted V. Не тратить время на общий pooling и раскладывание KV повторённых core passes по текстовому хешу.

Вторая попытка, с четырьмя представителями на **16**, не на 64 старых строках: `quadrature.py`, `quad-{code,reason,mixed200}.csv`. Query-independent balanced farthest-pair разбивает локальные K на четыре кластера, хранит медоид с его настоящим V либо отдельно FP16 mean K/V; каждому добавляется ln(4). Два наибольших по норме K в singleton-группах — ещё один контроль. Все три visits (5/23/47), все 24 heads, 4/4/3 позиций, ≥8192 точных hot rows. На code p95 gated L2 для стратифицированной случайной подвыборки/медоидов/cluster means: 61.5/54.0/57.4%, на reason 70.7/63.1/71.5%, на mixed200 63.4/75.4/80.1%. Это не результат для обученного глобального кодбука; дешёвая замена quarter-KV статическими локальными представителями слишком груба даже при учёте multiplicity и содержимого ключей.

## Free-running: что меняется у пользователя

Сначала на всех восьми visits включали **только** ограничение числа прочитанных рядов; KV остаётся физически полным, prefill `n>1` остаётся dense. Отдельно от тёплых тестов обе cold диагностические задачи реально решены на full scan: инструменты вызваны, естественные EOS; code 129 reasoning/204 output, reason 275/344. Эти trace прогоны с записью всех Q/K/V и состояния **не timing**. Основные измерения ниже — после строгого RESTORE идентичного префикса (время RESTORE указано в приложении). Грейдер проверяет результат, а не похожесть текста. `agent/SCREENS.md`, `agent/HISTORY.md`, `scoreboard.md`.

| 64K, одно и то же sampling, без форсирования | Dense | Последние 8192 | Последние 32768 |
|---|---:|---:|---:|
| Python clamp, 34 независимые проверки | pass, 6.34 с | pass, 6.59 с | pass, 6.17 с |
| Weighted population variance, требует цифр из live tool | pass, 8.30 с | **fail**, не вызвал tool | pass, **12.93 с** |
| Исторический контракт + runtime (две повторности одной задачи) | **2/2**, 4.85–6.55 с | **0/2**, 11.56–16.96 с до отказа | **0/2**, 13.00–13.66 с до отказа |

В variance 32K ускорил **оба** token loops, но потребовал 358 reasoning/427 выходных ID против 153/225 у dense (+56% к времени до правильного решения). В historic recall 8K/32K выбрали устаревшие инструменты и делали повторные запросы до лимита; это не доказательство, что отрезанный KV был единственной причиной, поскольку они даже не дошли до правильного tool return. Другой, гораздо более сильный тест: выбор четверти старых рядов стратифицированными блоками, ln(4), hot 8192 и весь последний user turn. Все 40 первых ID совпали, реальный ответ инструмента и **весь следующий вход** те же. Однако дальше модель гадала неверный offset и исчерпала 640 ID; **18.75 с без решения** против успешных 5.60 с. Простая выборка с ненулевой вероятностью доступа к любой старой позиции не решает задачу.

**Проверка, есть ли вообще смысл в лучшем отборе:** `liveoracle/REPORT.md` — native ROCm эксперименты, все восемь visits сами ранжируют настоящую массу на своих *текущих* запросах; модель не получает страницы/правильные ответы извне. На том же 64K historic кейсе **5%, 12.5% и 25% от старых страниц + 65 точно закреплённых страниц** решили задачу, каждая 189/189, один правильный вызов, без retries. Выбор *на голову*, не физический бюджет GQA. Это oracle на качестве, **не ускорение**: платит полным scan. Контроль all-pages переупорядочил редукцию: 3/50,688 полей Q8_1 не совпало на первых предикторах двух turns, второе рассуждение изменилось даже у него. 25%-arm совпал с этим (не stock!) контролем по всем 106 выходным ID, но множества восьми выбранных MoE experts отличались в **800/1920** и **1006/3168** visits двух turns. Совпавший текст не позволяет объявлять ни approximate KV, ни более широкую expert residency точными.

**Работающий отбор без oracle.** `select/README.md`, `select/history-v1.md`: сохраняем всю Q8 историю, 2 FP16 centroid (средние двух половин) на страницу 128, для каждого Q берём лучший dot и нормируем среди old pages, затем общий top-K для трёх heads. GPU radix-sort, выбранные страницы в хронологическом порядке; первая страница и минимум 2048 последних строк всегда доступны. Глобальный индекс 48.8125 MiB при max_ctx=200000 + до 200 KiB scratch: здесь физический KV не уменьшается, память **добавляется**. K=128/256 означает 128/256 *дополнительных страниц* на группу, а не CPU oracle B. На held-out 64K все четыре sparse и обе reference ноги прошли 189/189, один правильный tool, без ошибок/retries. При K256 ≈35,030 attended rows/group, 26 и 32 reasoning ID; успех 4.330/4.539 с vs dense 32 reasoning, 4.620 с. При K128 ≈18,648 rows/group, 33 reasoning, 4.486/5.342 с. На всех matched T1 ровно 40 одинаковых ID, T2 при одинаковом входе меняется. Дело не только в прижатой первой странице: обязательный архив находится в страницах 7–8, вне неё. При K256 ≈66K реальные cold attention leaf 464–483→314–322 µs/visit; score+sort ≈49 µs/visit. Успех этого индекса на конкретном кейсе и более резкое падение retained mass у простого min/max — основание пробовать centroid, а не основание включить его всем. Отличать all-pages control нативного селектора (сохранил арифметику stock в leaf) от all-pages *массового oracle* (другая редукция).

**Границы точных вариантов.** Снова запустил предыдущий lossless-кодек уже на неповторяющемся code+tools (`lossless-{64,197}.json`, `docs/goals/arch-decode-recon/kv/recon.py`; в 197K последняя часть — реальные исходники в скриптованных tool turns). 4224 из 4224 head-tile roundtrips в каждом. На этих двух histories практический hybrid даёт 2.33/2.51% projected payload (matched rounded mappings 2.19/2.51%). Это больше 0.80% из прежнего mixed near-cap, но не ликвидирует KV вытеснение. Диагностический zstd с лучшим transform постфактум, без цены произвольной выборки, 10.02/10.27%. Ни один процент не есть измерение GPU allocator или скорости. Отдельная проверка `heads/` — 192 single-Q-head interventions × 4 состояния, включая настоящий 13-й выдаваемый ID после tool. Одновременная замена gated FP32 и соответствующих 4 блоков Q8_1 с сохранением прочих heads/входа/placement. Dense A/A одинаков битово для каждого набора. Оmitted mass vs downstream TV при замене одной головы на окно 8192: Spearman лишь .098/.047 на первых mixed64/200; абсолютная L2 лучше (.332/.210), не предиктор успеха. В code EOS visit29/head18 достиг TV=.03564; отдельное пост-tool рассуждение имеет иную карту. Из этого нельзя вывести «локальную» группу или гарантированно несущественный проход на каждом токене.

Техническая оговорка для повторения: captured Q/relative уже после learned clip по норме головы и позиционного масштабирования, gate — до sigmoid. В `certificate.py` знаменатель — `Z_exact_kept+U_remaining`, доля страниц на **одну Q-голову среди old** (до обязательного recent и GQA union). У границ нет направленного округления: это численный replay, не сертификат FP32. У `repeatkv.py` одинаковые 128 ID **заканчиваются** на сравниваемой строке. Развёрнутая независимая проверка — `review-math.md`.

**Ещё две проверки границы.** (1) `zero_weight.py`: у 12.41M/12.41M/38.03M old head×key сравнений на code/tool, reason и mixed200 ни один score не отставал от global max, включая sink, даже на 80 (максимумы разностей 46.62/52.40/66.48). Поэтому у этих трёх реальных запросов нет страниц, которые exact FP32 scan может пропустить на основании underflow всех весов. Online max в штатном chunk ещё меньше. Это не формальное доказательство для произвольной модели. (2) `oracle/sparq/REPORT.md`: SparQ-подобный общий отбор по 32 самым сильным каналам тройки Q, температура по доле L1 query, рескоринг 8K точных ключей и поправка на mean V пропущенных. Два настоящих запроса из каждой истории, все visits/heads: p95 ошибки code/reason 23.1/18.8% без поправки → **13.65/12.58%** с ней. При 32K — 4.07/3.22%. Однако 8K затронули 93–96% 128-row pages. Теоретические 27% read от dense превращаются уже в ~62% при 16-byte lanes (без измерения шинных transactions), при B32K — в ~99%. Физическая выгрузка целой страницы не подходит к этому виду sparsity. Для редизайна в column-major пришлось бы дополнительно оплатить хранение K и его обновление.

**Тот же случай с закреплением первых 2048 строк.** На том же 65K historic prefix stride-4 прошёл при anchor=2048 (4.93 с), а при anchor=0 опять упёрся в length (18.85 с); dense 5.31 с. Это проверка механизма, **не** основание считать prefix pin универсальным: вся нужная запись `[905,1052)` была непосредственно защищена. Поэтому данные нового стресс-теста живут в **середине**: в старом tool result на позициях `[65888,66034)` 197K истории. `longagent/README.md`: первые 65,796 ID из настоящего завершённого интерактивного CPython transcript, дальше в отдельных *скриптованных* turns добавлены уникальные настоящие исходники Python и архивная таблица. Никакие правильные output IDs не подставлялись. Нативные snapshots 129,015 и 197,021, подтверждён весь наследуемый global KV соответственно 1,145,376,768 и 2,245,893,120 байт. Три новые free-running задачи — возврат старой таблицы + live lookup, старые clipping bounds + текущие inputs и current-only контроль. На 129K dense прошёл 3/3 за 8.03–9.35 с; W8K 0/3 с незавершённым JSON и без выполненных tools даже на current-only. Не называть это чистым тестом retrieval.

## Как перейти от эксперимента к реализации

1. **Оставить dense Q8 опорным и полностью доступным.** Не включать окно как автоматическую реакцию на недостаток VRAM. В режиме строгой точности — прежняя арифметика и бюджет экспертов, общий SWA scratch из прошлой работы; отдельно проверять exact dense W1 kernel scheduling. Для каждой замены сравнивать *все* захваченные FP32, частичные суммы, Q8_1 и нативную сессию, а не только текст или top-1. Из 40 local visits нового линейного выигрыша получить нельзя. Запускать exact kernel только там, где same-day untraced выигрыш отделим от A/A, ROC подтверждает причину, и ни p90, ни агентская latency не ухудшились.
2. **Read-first, без новой политики размещения.** Отдельный opt-in на target/Q8/serial W1 из `src/poly/inkling2.cu::{store,attention,run_visits}` и `src/poly/inkling_attend.cu::attend_decode`. Начинать от плотного восстановления и двухполустраничных centroid, K256/P128, хронологический порядок выбранных ключей. Сохранить настоящий projected sink и gate, absolute relative distance и последний chunk. Не сериализовать derived index; на partial-page overwrite, verifier `keep`, checkpoint/prefix reuse, RESTORE и смену sequence либо гарантированно обновить и удалить stale pages, либо инвалидировать и перестроить перед первым W1. Dense prefill/verify в первой версии; учесть стоимость построения/перестроения в холодном TTFT и после tool. Всё состояние каждого visit независимо. Порог длины/выгодности определять по замерам отдельно; для коротких spans оставлять штатный путь. Наряду с off иметь all-pages *контроль* оригинальной редукции. Сомнительный fetch и короткий служебный turn не перекладывать автоматически на малый бюджет. Измерить, окупается ли fallback в сложных фазах на независимых запросах.
3. **Capacity отдельно от reads.** Если тестировать более компактный VRAM layout, хранить полные K, оригинальный hot Q8 и упакованные cold V по visit; с отдельными physical backing и byte accounting в `alloc_caches()`, `Engine::cover()`, `mind_vram()`. Сначала тот же expert map (важно и на prompt split, и после restore), потом отдельная политика «финансированных» новых slots; сверять DRM fdinfo, mapped KV/arena, transfer bytes и hits после реального роста. Увеличивать на целые **реально оплаченные** страницы арены, не вычитать абстрактный budget и не трогать reserve. Нужен seal при естественном росте с учётом незавершённых страниц/verifier; прототипы кодеков запечатывают только уже восстановленный immutable prefix. Не путать canonical disk Q8 с резидентным V4: при SAVE/rewind, prefix reuse и переключении на dense нужны оригиналы из RAM/родительского snapshot или отражающий формат отдельный version/fingerprint. Потерянные биты из V4 не восстановить. Не записывать деквантованное приближение как точную старую сессию. Тестировать `save_card_rows/load_card_rows`, границу seal и долгие многоходовые prompt extensions; учесть, что сегодня на таких батчах fallback mixed-dense вместо Flash способен съесть выигрыш TG на втором TTFT. Полный архив на CPU не означает перечитывать его на каждом шаге.
4. **Решение по качеству принимается на каждой комбинации заново.** Не складывать ускорение селектора и «освобождённые slots» из разных прогонов. Минимальная следующая acceptance-матрица: matched dense A/A, compute-only A/B, capacity-only при том же map, тот же codec с расширенным map, комбинация. Один и тот же исходный state/profile и семена; не replay output IDs в semantic benchmark. Цена построения/restore/длинного tool return + warm TG/P90 и время до верного решения. На stratified held-out tracks разместить независимые реальные указания в начале, середине и конце, отвлекающие похожие файлы, короткие и длинные user turns; оставить задачу, где dense иногда ошибается, с отдельной частотой baseline. Несколько случайных семян и новых репозиториев, одна и та же граница tokens/вызовов и один grader для обеих arms. Рабочая точка с ошибками/retries или удлинившимся reasoning не проходит только за счёт высокого TG. Сначала идентичное размещение и холодная/тёплая проверка, затем только по просьбе владельца — opt-in pilot, не менять defaults по данным одной машины/задачи.

`wall-time.md` декомпозирует наблюдаемое время пар *успешных* runs на число шагов, cadence и TTFT. Например, у variance W32K изменения +5.98 с из-за длины и −1.33 с от более быстрого token loop, итого **+4.63 с** целиком. У K256 в быстрейшем архивном 64K run −0.20 из −0.29 с объясняется более короткой репликой. Это арифметическое разложение, не counterfactual по качеству. За абсолютные TG не выдавать исторические release числа; noisy workstation, guard запрещает параллельные benchmark processes на GPU, но не скрывает CPU/desktop jitter.

**Duo и фазовые правила.** Статическая маска, обученная только на первом code-64K, держит full 32/64 группы (все 8 у visit 5, по одной у 23 и 35), остальные держат prefix 2048, hot 8192 и текущий user turn. History и variance прошли 189/189 и JSON с верными числами; выборка изменилась. 47.4% меньше *логических* group-row bytes не дало аналогичного ускорения: **20.28 → 20.88 IDs/s**, p50 48.22 → 46.97 мс, без экономии VRAM. Не ускорять план переходом к статически обрезанным группам. `duo/REPORT.md`. Проба `phase/`: окно+anchor включается только внутри reasoning; на history обе задачи прошли, 4.859 → 4.804 с, не доказательство выигрыша. Второй парный сценарий исключён: control до генерации отклонил native RESTORE с `payload checksum mismatch` при неизменном SHA на диске; третий не запускался. Успешные prefill/restore других серий не считать измерением этого пути. На независимой реальной задаче `tickets/RX-*` одно окно 8K заставило перечитать два куска `argparse.py`: 1 → 3 calls, 97 → 206 reasoning, 188 → 404 output и **10.06 → 16.53 с** до корректного JSON; stride-4 вообще не дошёл до EOS. При `CV` 8K тоже решает, но 26 → 93 reasoning и 7.89 → 9.11 с. Это объясняет, почему telemetry loop t/s недостаточно.

**Прямая проверка комбинации, не сумма двух ускорений.** [`combined-reader.md`](combined-reader.md): один физический mixed reader, в варианте B — тот же reader с K256. 199104: Q8 cover 3320.31, оба refit mmap 2550.81 MiB, обе арены 2304 MiB/536 slots, strict combined cap 4900 MiB (`4832+68` начальных growing KV), reserve 2048. В других v2 сериях «4900» означает аргумент калибровки на входе (native centroid combined 4968 MiB), а не идентичные физические 4900. Все выбранные строки читались из VRAM. Все 512/512 W1 global visits кандидата выбрали 256 старых страниц без silent fallback, входной prompt predictor dense. **35,037.5 против 199,137.5 rows** в среднем на группу/visit, −82.4% чтений рядов, не измеренный % трафика DRAM. CPU независимо воспроизвёл picked pages на реальном visit 5 во всех группах с max |ΔFP32| 3.10е−6. Новые `drm-resident-vram` 7916.56 → 7964.86 MiB после restore. Дополнительный индекс оплачивается поверх 769.5 MiB экономии codec. Все 65 greedy ID одинаковы; TG **20.72 → 25.95** по *всем* интервалам, p90 **54.44 → 45.61 мс**; симметрично отбросив интервал единственного probe — **20.75 → 26.01**. Короткая одиночная пара.

Сравнения с Q8-K256 в том же бинарнике и при том же cap нет: не складывать +19.1% и +25.3%; 26.01 не доказательство превосходства по времени задачи над Q8-K256. ### Приоритет следующей итерации

* **Точность обязательна:** оставить dense Q8 + прежнее размещение. Уточнить порог только для order-preserving dense ядра на near-cap; даже 0.172 мс из 45–50 мс даёт менее 0.4% при идеальном переносе, не 10%. Не тратить следующий цикл на обещание точного sparse режима по порогу массы.
* **Сохранить рабочий coding/reasoning при большей скорости:** первым A/B в opt-in сделать Q8-K256 без смены размещения. На 64K нет подтверждённого выигрыша decode; near-200K планировать проверку **~23–24 ID/с**, не обещать 30+ или сохранение прежней траектории. Нужна именно *агентская* ступень 128K для K256: есть kernel data на этом span и агентские провалы fixed-window, но нет основания интерполировать успехи K256 между 64 и 197K. На сложности/неуверенности сохранять возможность dense Q8; уже записанную изменённую траекторию переключение не отменяет.
* **Если нужен ещё и VRAM:** второй opt-in — `Q8 K + cold V4-refit + K256`. Сначала один ELF и один совокупный лимит для Q8-dense/Q8-K256/V4-dense/V4-K256 на одинаковых cold/warm входах. Отдельно фиксированное/профинансированное размещение экспертов. Далее seal при естественном росте, canonical save/restore и длинные tool returns; без этого эксперимент покрывает продолжение из snapshot, а не работающий сервер. Зафиксировать сдвиг точности и эффективность **на задачу**, не выдавать `all-pages` на V4 за восстановление точных V8.
* **Условие продвижения, предлагаемое для следующего этапа:** сравнивать долю решённых при одном бюджете времени/turns и без forced outputs, число повторных ошибок, reasoning IDs, wall до grade, p90 и расход VRAM. Crossover AB/BA с независимыми задачами и семенами, отделить ресторы от cold; неопределённость оценивать по запросам/запускам, не по токенам одной реплики. Если на допущенной точке больше отказов, а fallback не возвращает исходный уровень успеха с выигрышем wall — не продвигать. Не убирать из denominator неудачные/оборванные траектории. Если качество сохраняется, но wall проигрывает из-за длинного prefill/регенерации, следующий профиль — этот этап, а не новое ужатие KV.
